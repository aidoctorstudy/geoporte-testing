# Internationalization — Language Switcher

The nav language switcher covers **nav links, section headings, and button
labels** (not full body copy — see [[decisions-log]] ADR-0024 for the scope
call). Languages: English (default), Arabic, Urdu, French, Chinese. `ar`/`ur`
flip the whole document to RTL.

No i18n framework is installed — this is built from pieces already in the
stack ([[tech-stack]] → "Internationalization"): `zod`, `zustand`, and the
existing `app/api` / `apiFetch` convention.

## How a string gets translated

1. A component calls `useTranslated("Contact Us")` (or renders
   `<TranslatedText text="Contact Us" />` inside a `.map()`, where a bare hook
   call would break the rules of hooks).
2. If the current language is `"en"`, or the string is already cached for the
   current language, it returns immediately — no request.
3. Otherwise it queues the string via `queueTranslation` (`lib/i18n/translation-queue.ts`),
   which batches every string queued within a 120ms window into **one**
   `POST /api/translate` call per language, rather than one request per string.
4. The route (`app/api/translate/route.ts`) validates the payload with `zod`
   and proxies to a LibreTranslate instance — the browser never calls it
   directly (hard rule #9 / [[api-architecture]]).
5. Results are cached in the `zustand` store (`hooks/i18n/use-language-store.ts`),
   persisted to `localStorage` under `geoporte-language` — so a string is only
   ever translated once per language, across reloads too.
6. **Fallback:** if the upstream call fails (rate-limited, unreachable, …),
   the string is simply left uncached and `useTranslated` keeps returning the
   English source text. There is no error state shown to the user.

## RTL

`<LanguageDirection>` (`components/common/LanguageDirection.tsx`) is mounted
once at the app root next to `<ReducedMotion>`. It watches the language store
and sets `document.documentElement.lang` / `dir`. Components that need
direction-aware positioning (e.g. the language dropdown itself) use Tailwind's
logical-property utilities (`start-*`/`end-*`, `text-start`) instead of
`left-*`/`right-*`, so they flip automatically under `dir="rtl"`.

## Headings & `TextEngine`

`<SectionHeading>` (`components/common/SectionHeading.tsx`) wraps the
eyebrow + `TextEngine` heading pattern repeated across every homepage section.
It's a client component that resolves both strings through `useTranslated`
before handing them to `TextEngine` as plain strings — `TextEngine` never sees
an unresolved translation component as a child (its word/letter splitting
reads `children` directly, so a custom component wouldn't render its text
until React actually renders it — passing pre-resolved strings sidesteps that
entirely).

Because `useLanguageStore`'s initial state is always `"en"` (it only rehydrates
from `localStorage` client-side, after hydration), the server-rendered HTML —
and the `TextEngine` `seo` hidden-copy fallback — is always English. A saved
non-English preference swaps the visible text in client-side, after mount.

## Server-side proxy

See [[api-architecture]] for the general convention. The translate route:

- Validates `{ texts: string[], targetLang: "ar"|"ur"|"fr"|"zh" }` with `zod`
  (max 50 strings, max 500 chars each, per call).
- Defaults to the public `https://translate.disroot.org` instance;
  `LIBRETRANSLATE_ENDPOINT` (server-only env var) overrides it for a
  self-hosted instance.
- Returns `{ translations: string[] }` in the same order as the input, via the
  `handle()` envelope.
